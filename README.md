# Система бронирования столиков в ресторане (Лабораторная работа 5)

## Тема проекта
Проект представляет собой систему управления рестораном, а именно — бронированием столиков. Приложение позволяет управлять клиентской базой, списком ресторанов, столиков и меню, а также предоставляет полноценную логику для бронирования столиков на определенное время с учётом их доступности и вместимости.

В **пятой лабораторной работе** механизм аутентификации был переработан: вместо базовой авторизации (Basic Auth) реализована **JWT-аутентификация** с поддержкой **Refresh-токенов** и **ротацией сессий** для защиты от повторного использования токенов.

## Основные сущности
- **User (Пользователь)** — сущность для аутентификации в системе, хранит логин, зашифрованный пароль (BCrypt) и роль (`ROLE_USER` или `ROLE_ADMIN`).
- **UserSession (Сессия пользователя)** — хранит пару токенов (access + refresh), идентификатор устройства, время жизни и статус сессии.
- **Customer (Клиент)** — содержит информацию о клиентах (имя, телефон, почта).
- **Restaurant (Ресторан)** — информация о заведении (адрес, часы работы).
- **Table (Столик)** — столики в ресторане (вместимость, доступность, расположение).
- **MenuItem (Пункт меню)** — список позиций меню (цена, категория, доступность).
- **Reservation (Бронирование)** — связывает клиента и столик на определённое время, хранит продолжительность, количество гостей и статус.

## JWT-аутентификация и управление сессиями

### Архитектура токенов
Приложение использует двухуровневую схему токенов на базе библиотеки **JJWT 0.11.5**:

| Токен | Время жизни | Назначение |
|---|---|---|
| **Access Token** | 15 минут | Передаётся в заголовке `Authorization: Bearer <token>` при каждом запросе к защищённым эндпоинтам |
| **Refresh Token** | 7 дней | Используется **только** для получения новой пары токенов через `/auth/refresh` |

Оба токена подписываются симметричным ключом HS256 и содержат поле `tokenType` (`"access"` или `"refresh"`), что позволяет фильтру отклонять refresh-токены при обращении к API.

### Ротация сессий (Refresh Token Rotation)
Каждая сессия (`UserSession`) имеет один из трёх статусов:

| Статус | Описание |
|---|---|
| `ACTIVE` | Сессия действительна, refresh-токен можно использовать |
| `USED` | Refresh-токен уже был обменян — сессия считается завершённой |
| `REVOKED` | Сессия аннулирована (обнаружено повторное использование токена) |

**Защита от повторного использования:** если клиент попытается использовать уже применённый refresh-токен (статус `USED`), сессия немедленно переводится в статус `REVOKED`, а запрос отклоняется с ошибкой `401`.

### Фильтр аутентификации (JwtAuthenticationFilter)
`JwtAuthenticationFilter` перехватывает каждый HTTP-запрос, извлекает токен из заголовка `Authorization`, валидирует его и устанавливает контекст безопасности Spring Security.

## Эндпоинты аутентификации

| Метод | URL | Доступ | Описание |
|---|---|---|---|
| `POST` | `/auth/register` | Публичный | Регистрация нового пользователя (роль `ROLE_USER` по умолчанию) |
| `POST` | `/auth/login` | Публичный | Вход по логину/паролю, возвращает `accessToken` и `refreshToken` |
| `POST` | `/auth/refresh` | Публичный | Обновление пары токенов по действующему `refreshToken` |

### Пример запроса `/auth/login`
```json
POST /auth/login
Content-Type: application/json

{
  "username": "user1",
  "password": "secret"
}
```

### Пример ответа
```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
  "refreshToken": "eyJhbGciOiJIUzI1NiJ9..."
}
```

### Пример запроса `/auth/refresh`
```json
POST /auth/refresh
Content-Type: application/json

{
  "refreshToken": "eyJhbGciOiJIUzI1NiJ9..."
}
```

## Разграничение прав доступа к API

| Права | Эндпоинты |
|---|---|
| Публичный доступ | `POST /auth/register`, `POST /auth/login`, `POST /auth/refresh` |
| `ROLE_USER` и `ROLE_ADMIN` | `GET /api/**` — просмотр ресторанов, меню, доступных столиков |
| `ROLE_ADMIN` | `POST`, `PUT`, `DELETE /api/**` — создание, изменение, удаление данных |

> Роль Администратора выдаётся путём ручного изменения поля `role` пользователя в базе данных PostgreSQL.

## Операции сервиса
Сервис поддерживает базовые CRUD-операции для всех бизнес-сущностей, а также **5 выделенных бизнес-операций** в логике бронирования:

1. **Создание бронирования** (`POST /api/reservations`) — проверяет существование клиента и столика, его доступность, вместимость и отсутствие пересечений по времени.
2. **Отмена бронирования** (`PUT /api/reservations/{id}/cancel`) — перевод брони в статус `CANCELLED`.
3. **Завершение бронирования** (`PUT /api/reservations/{id}/complete`) — перевод брони в статус `COMPLETED` (допустимо только из `CONFIRMED`).
4. **Поиск доступных столиков** (`GET /api/reservations/available`) — поиск столов, свободных на заданное время и дату для нужного количества персон.
5. **Перенос времени бронирования** (`PUT /api/reservations/{id}/reschedule`) — изменение времени существующей брони с проверкой пересечений.

## Технологии
- **Spring Boot 3** — основной фреймворк
- **Spring Security** — управление доступом
- **JJWT 0.11.5** (`jjwt-api`, `jjwt-impl`, `jjwt-jackson`) — генерация и валидация JWT
- **Spring Data JPA + PostgreSQL** — хранение данных и сессий
- **Lombok** — сокращение шаблонного кода
- **Spring Validation** — валидация входящих DTO

## Настройка и запуск

### Переменные окружения (`.env`)
```
DB_HOST=localhost
DB_PORT=5432
DB_NAME=restaurant_db
DB_USER=postgres
DB_PASSWORD=postgres
```

### Запуск
```bash
mvn spring-boot:run
```

Приложение запускается на порту `8080` (HTTP).

> Все конфигурационные и чувствительные данные (URL базы данных, логин, пароль) вынесены в файл `.env`.
