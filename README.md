# Система бронирования столиков в ресторане (Лабораторная работа 4)

## Тема проекта
Проект представляет собой систему управления рестораном, а именно — бронированием столиков. Приложение позволяет управлять клиентской базой, списком ресторанов, столиков и меню, а также предоставляет полноценную логику для бронирования столиков на определенное время с учетом их доступности и вместимости.

В **четвертой лабораторной работе** в проект была добавлена система безопасности и авторизации на базе **Spring Security**. Реализована аутентификация пользователей, шифрование паролей и ролевая модель доступа.

## Основные сущности
- **User (Пользователь)** - сущность для аутентификации в системе, хранит логин, зашифрованный пароль (BCrypt) и роль (ROLE_USER или ROLE_ADMIN).
- **Customer (Клиент)** - содержит информацию о клиентах (имя, телефон, почта).
- **Restaurant (Ресторан)** - информация о самом заведении (адрес, часы работы).
- **Table (Столик)** - столики в ресторане (вместимость, доступность, расположение).
- **MenuItem (Пункт меню)** - список позиций в меню ресторана (цена, категория, доступность).
- **Reservation (Бронирование)** - связывает клиента и столик на определенное время, хранит продолжительность, количество гостей и статус.

## Безопасность и Авторизация (Spring Security)
В приложении настроена классическая базовая авторизация (**Basic Authentication**). Доступ к API строго регламентирован в зависимости от роли пользователя:
- **Открытые эндпоинты**:
  - `POST /auth/register` — регистрация новых пользователей. При регистрации пользователь по умолчанию получает роль `ROLE_USER`.
- **Права `ROLE_USER` (и `ROLE_ADMIN`)**:
  - `GET /api/**` — доступ ко всем операциям чтения (просмотр ресторанов, меню, доступных столиков).
- **Права `ROLE_ADMIN`**:
  - `POST`, `PUT`, `DELETE /api/**` — доступ к модификации данных (добавление новых ресторанов, создание и отмена бронирований, изменение меню).
  
*Примечание:* Защита от CSRF-атак отключена для путей `/api/**` для удобства тестирования через Postman. Роль Администратора выдается путем ручного изменения поля `role` пользователя в базе данных PostgreSQL.

## Операции сервиса
Сервис поддерживает базовые CRUD-операции для всех бизнес-сущностей, а также **5 выделенных бизнес-операций** в логике бронирования:

1. **Создание бронирования** (`POST /api/reservations`) — сложная операция, проверяющая:
   - Существование клиента и столика.
   - Доступность столика (`isAvailable == true`).
   - Вместимость (чтобы гостей было не больше, чем вмещает столик).
   - Пересечение по времени (чтобы столик не был занят другими в этот период).
2. **Отмена бронирования** (`PUT /api/reservations/{id}/cancel`) — перевод брони в статус "CANCELLED".
3. **Завершение бронирования** (`PUT /api/reservations/{id}/complete`) — перевод брони в статус "COMPLETED" (допустимо только из статуса "CONFIRMED").
4. **Поиск доступных столиков** (`GET /api/reservations/available`) — поиск столов, которые свободны на заданное время, дату и для нужного количества персон.
5. **Перенос времени бронирования** (`PUT /api/reservations/{id}/reschedule`) — изменение времени существующей брони с проверкой пересечений.

> Все конфигурационные и чувствительные данные (URL базы данных, логин, пароль) вынесены в файл `.env`.
> В проекте используется Spring Data JPA для реализации слоя доступа к данным (PostgreSQL).
